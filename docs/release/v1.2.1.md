# lsm-db v1.2.1 - Drop keeps writes

**Dropping an `Lsm` no longer loses writes that were never flushed.** The API,
the on-disk format, and every checksum are the same as 1.2.0.

## Fixed

- **Data loss on drop.** In a build without the `durability` feature (the
  default), `Drop` stopped the background compactor and discarded the
  in-memory buffer, so `put` followed by a clean exit without `flush` lost
  the write. `tests/drop.rs` reproduces it on 1.2.0: put, drop, reopen, and
  the key is gone. `Drop` now stops the compactor and then flushes. An error
  from that flush cannot be reported from `Drop`, so call `flush` first where
  the caller needs to see one. With `durability` on, the writes were already
  in the log and recovered at the next open; the flush now saves that
  replay.

## Changed

- The bloom sidecar's dependencies are pinned: `bloom-lib` to `=1.0.0`, and
  `postcard` to its 1.1 patch releases. The sidecar bytes are frozen for 1.x,
  and bloom-lib does not yet promise a stable byte layout.

## Security

- A golden-file test (`tests/data/bloom-sidecar-v1.bin`) checks the bloom
  sidecar bytes. The file is byte-identical to a sidecar written by the
  published 1.2.0. The test decodes it, re-encodes it to the same bytes, and
  builds a fresh filter over the same keys with the same bytes, so a
  dependency update that changes the layout fails CI.

## Upgrading

Nothing to do: `lsm-db = "1.2"`. A program that relied on a drop discarding
unflushed writes (to simulate a crash, say) should use `std::mem::forget`
instead, as the crate's own durability tests now do. The MSRV stays 1.85.
