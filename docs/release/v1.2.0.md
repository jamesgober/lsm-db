# lsm-db v1.2.0 - No third-party dependencies

**A default build of `lsm-db` brings in no third-party crate.** The engine, its
API, the on-disk format, and every checksum it writes are the same as 1.1.

## What changed

- **CRC32C in the crate.** The `crc32c` crate is gone from `[dependencies]`.
  A `std` build asks the CPU at run time and uses the SSE4.2 `crc32`
  instruction on x86_64 or the ARMv8 CRC extension on aarch64, interleaving
  three streams to hide the instruction's latency, with slicing-by-8 tables on
  other CPUs: the same code a `no_std` build has used since 1.1.
- **Byte-identical checksums.** The tests check every path against the
  published CRC32C vectors (the CRC catalogue check value and RFC 3720 B.4) and
  against the `crc32c` crate, kept as a dev-dependency only, on every length
  and alignment across the loop boundaries.
- **`error-forge` 1.1 and `wal-db` 1.2**, neither of which brings in a
  third-party crate. `cargo tree -e normal` for a default build:
  `lsm-db`, `error-forge`, `error-forge-derive`.
- **`unsafe`:** a `std` build on x86_64 or aarch64 now compiles the hardware
  module (the CRC intrinsics, and the one function compiled with the feature
  on, called only after the CPU said it has it). Every other build still
  forbids `unsafe` outright.

## Measured

Windows, x86_64, release, 1.1 and 1.2 alternating in one job:

| Benchmark | 1.1 | 1.2 |
|---|---|---|
| CRC32C, 64 bytes | 11 ns | 4.4 ns |
| CRC32C, 4 KiB | 163 ns | 150 ns |
| CRC32C, 64 KiB | 2.2 us | 2.2 us |
| flush of 20,000 values of 100 bytes | 37.9, 23.7 ms | 26.2, 23.7 ms |
| open with 8 runs | 1.2, 3.4 ms | 2.9, 2.5 ms (file system bound, noisy) |
| get spread over 8 runs | 487, 414 ns | 515, 444 ns |
| get hit / miss from a run | 379 / 175 ns | 393 / 162 ns |

A software-only CRC (no hardware path) measured about 2 GB/s against 22 GB/s,
roughly ten times the cost on every block written or read from disk; that is
why the hardware path stays.

## Upgrading

Nothing to do: `lsm-db = "1.2"`. The MSRV stays 1.85.
