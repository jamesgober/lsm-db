# lsm-db v1.1.0 - Real no_std

**`default-features = false` now builds on bare-metal targets, and carries the
on-disk format with it.** Nothing changes for `std` users: the engine, its API,
the on-disk format, and the checksums it writes are the same as 1.0.

## What was wrong

`lsm-db` declared `#![no_std]` when the `std` feature was off, but `crc32c` and
`error-forge` were unconditional dependencies and both need the standard
library. A `default-features = false` build failed on any `no_std` target
([#2](https://github.com/jamesgober/lsm-db/issues/2)). And even where it
compiled, it exported nothing: every module sat behind `std`.

## What 1.1 does

- **`crc32c` and `error-forge` are optional**, pulled in by `std` (on by
  default). The `ForgeError` impl and `Error::Io` exist only with `std`.
- **A `no_std` CRC32C** in `src/crc.rs`. Without `std` there is no run-time CPU
  detection, so the choice is made at compile time: the SSE4.2 `crc32`
  instruction on x86_64 or the ARMv8 CRC extension on aarch64 when the target
  enables them (`-C target-feature=+sse4.2` / `+crc`), with the same
  three-stream interleave as the `crc32c` crate, and slicing-by-8 tables
  otherwise. The `std` build still uses the `crc32c` crate.
- **The `format` module**: the sorted-run format as an in-memory codec, built
  without `std`. `RunWriter` encodes entries into a run and `RunReader`
  validates a run in a byte buffer and serves `get` and in-order iteration,
  borrowing keys and values from the buffer. `RunWriter` output is
  byte-identical to the file the engine writes for the same entries, so a run
  built on a device opens on a host and the other way round.
- **An `alloc` feature** (implied by `std`) enables `RunWriter` / `RunReader`.
  Without it, a `no_std` build still has `format::crc32c`, `format::Entry`,
  the length limits and the error type, and needs no allocator.
- `durability` and `bloom` now imply `std`; both need a filesystem.

```toml
[dependencies]
lsm-db = { version = "1.1", default-features = false, features = ["alloc"] }
```

## Checksums are bit-identical

The on-disk format depends on CRC32C, so every path is tested against the
`crc32c` crate and against published check values (the CRC catalogue value for
`123456789` and the RFC 3720 iSCSI vectors), across every length and alignment
boundary of the hardware path. CI runs those tests on the table path (x86_64),
the SSE4.2 path (x86_64 with `+sse4.2`) and the ARMv8 path (Apple silicon).

Throughput on the dev machine (Windows, x86_64, from
`benches/crc.rs`):

| Build | 4 KiB | 64 KiB |
|-------|-------|--------|
| `std` (`crc32c` crate, unchanged) | 7.6 GiB/s | 7.3 GiB/s |
| `no_std`, `+sse4.2` | 38.7 GiB/s | 36.5 GiB/s |
| `no_std`, table | 2.6 GiB/s | 2.5 GiB/s |

The engine benchmarks (`benches/lsm_bench.rs`), run interleaved against 1.0.0,
show no regression.

## Other fixes

- **Over-long keys and values are rejected.** The format caps every length at
  2^30 bytes, but `Lsm::put`, `delete` and `write` accepted more, so the write
  succeeded and the flushed run then read back as corrupt (and could stall
  compaction). They now return the new `Error::InvalidInput` before anything is
  logged or buffered.
- **Out-of-range block extents** in a run's index are now reported as
  `Error::Corruption` when the run is opened, as the format spec requires,
  instead of surfacing later as an I/O error.
- `docs/SSTABLE_FORMAT.md` now defines the checksum by its parameters and check
  value rather than by naming a crate.

## unsafe

The default build is still `#![forbid(unsafe_code)]`. The one exception is a
`no_std` build whose target enables the CRC instructions: calling those
intrinsics takes `unsafe` on every Rust version, so that configuration has four
one-line `unsafe` blocks in `src/crc.rs`, each sound because the instruction is
guaranteed by the compile-time target feature.
